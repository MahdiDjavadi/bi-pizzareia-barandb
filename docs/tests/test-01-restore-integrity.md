# تست 01: بازیابی و صحت‌سنجی یکپارچگی داده‌ها

**فاز / مرحله:** P2 / S0–S1

## هدف

بازیابی نسخه پشتیبان به‌عنوان یک دیتابیس جدید از یک سیستم عملیاتی، تأیید صحت ساختاری دیتابیس بازیابی‌شده و محافظت از منبع در برابر هرگونه تغییر.

## کاری که انجام شد

دیتابیس در یک پایگاه داده جدید بازیابی شد. سپس با اجرای `DBCC CHECKDB` یکپارچگی ساختاری آن بررسی شد و در نهایت دیتابیس در حالت فقط‌خواندنی (`READ_ONLY`) قرار گرفت.

**اسکریپت:** `sql/discovery/t01_restore_integrity.sql`

## نتیجه

### مشخصات فایل backup

| مورد | مقدار |
|---|---|
| نام دیتابیس | `BaranDb` |
| حجم فایل پشتیبان | حدود 272 مگابایت |
| نسخه فرمت دیتابیس (`DatabaseVersion`) | 957 (SQL Server 2022) |
| تاریخ ایجاد دیتابیس | 2024-10-15 |
| زمان تهیه نسخه پشتیبان | 2025-12-22 18:07 |
| محیط بازیابی | SQL Server 2025 |
| سطح سازگاری (`Compatibility Level`) | 160 (بدون تغییر) |
| Collation | `Persian_100_CI_AS` (بدون تغییر) |
| نتیجه `DBCC CHECKDB` | بدون خطا |
| وضعیت دیتابیس | `READ_ONLY` |

## نکته مهم

اجرای `DBCC CHECKDB` یکپارچگی ساختاری دیتابیس بازیابی‌شده را تأیید کرد؛ اما به‌تنهایی صحت مقادیر داده‌ها، یکتایی کلیدهای احتمالی یا وجود رکوردهای یتیم (Orphan Records) را مشخص نمی‌کند. این موارد در مراحل بعدی و با آزمون‌های داده‌ای جداگانه بررسی خواهند شد.

برای حفظ محرمانگی، نام کسب‌وکار، مسیر فایل‌ها و هش فایل پشتیبان منتشر نمی‌شوند.

## تفسیر

- **محتمل:** تاریخ ایجاد دیتابیس (`2024-10-15`) ممکن است نشان‌دهنده زمان نصب یا مهاجرت این نسخه از سیستم باشد، نه زمان آغاز فعالیت کسب‌وکار.
- تاریخ تهیه نسخه پشتیبان (`2025-12-22`) صرفاً زمان ثبت نسخه پشتیبان را نشان می‌دهد و معادل تاریخ پوشش داده‌های کسب‌وکار (Business As-of Date) نیست. تاریخ پوشش داده‌ها در مرحله T04 و بر اساس خود داده‌ها تعیین خواهد شد.
